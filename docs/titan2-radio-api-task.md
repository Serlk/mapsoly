# Задача: API сотовых измерений и Bluetooth на Titan 2 (Alpine)

Заказчик — приложение mapsoly (Flutter, работает от пользователя `serlk`, не root).
Оно определяет позицию без GPS по сотам, Wi-Fi и BLE, поэтому ему нужны
измерения радиоокружения: какие станции слышны, с каким уровнем и насколько
свежие данные.

Состояние на 2026-11-26: ModemManager с плагином `mtk-ccci` отдаёт только
обслуживающую соту (`3gpp-lac-ci`: MCC/MNC, TAC, Cell ID). Соседних сот,
уровней сигнала по сотам и Timing Advance нет. `bluetoothctl show` отвечает
`No default controller available`.

## 1. Соты

### Что нужно

Реализовать в плагине `mtk-ccci` стандартный метод ModemManager
`org.freedesktop.ModemManager1.Modem.GetCellInfo()` (он же
`mmcli -m N --get-cell-info`). Свой отдельный API придумывать не надо:
стандартный метод уже описывает нужные поля, а приложение заработает и на
других Linux-телефонах.

Если в плагине это сделать нельзя, запасной вариант — отдельный сервис на
системной шине D-Bus с тем же набором полей и теми же именами ключей.

### Какие соты

- Обслуживающая сота каждого модема (в системе их два, по одному на SIM).
- Все соседние, которые модем измеряет: на той же частоте, на других
  частотах и в других технологиях.
- Вторичные несущие при агрегации и NR-сота в режиме NSA, если модем их отдаёт.

### Поля

Имена ключей — как в `MMCellInfo*` ModemManager.

| Технология | Идентификация | Измерения |
|---|---|---|
| LTE | `operator-id`, `tac`, `ci`, `physical-ci`, `earfcn` | `rsrp`, `rsrq`, `timing-advance`, `bandwidth` |
| NR | `operator-id`, `tac`, `ci`, `physical-ci`, `nrarfcn` | `rsrp`, `rsrq`, `sinr`, `timing-advance` |
| UMTS | `operator-id`, `lac`, `ci`, `psc`, `uarfcn` | `rscp`, `ecio` |
| GSM | `operator-id`, `lac`, `ci`, `base-station-id`, `arfcn` | `rx-level`, `timing-advance` |

Плюс для каждой записи `cell-type` и `serving`.

Соседние соты обычно приходят без `ci` и `tac` — это нормально, достаточно
`physical-ci` + `earfcn` + уровня. Но если модем их знает, отдавать.

### Правила

- **Отсутствующее значение — отсутствующий ключ.** Не подставлять 0, 255,
  0x7FFFFFFF и прочие заглушки модема: приложение не отличит их от измерения.
- **Timing Advance отдавать сырым**, как сообщает модем, без пересчёта в метры.
  В описании результата указать, в каких он единицах. Вне соединения его
  обычно нет — тогда ключ отсутствует.
- **Свежесть.** Каждый вызов возвращает текущие измерения, а не кэш с момента
  регистрации. Если кэш неизбежен, он не старше 2 секунд.
- **Частота опроса.** Приложение будет вызывать метод раз в 2–5 секунд во
  время навигации. Это не должно рвать передачу данных, мешать звонкам и SMS.
- **Питание.** Когда метод никто не вызывает, дополнительных пробуждений
  модема быть не должно.
- **Доступ.** Вызов должен проходить от пользователя `serlk` без root и без
  интерактивного запроса прав.
- **Ошибки.** Модем выключен, режим полёта, нет SIM — возвращать ошибку
  D-Bus, а не пустой список. Пустой список означает «сот не слышно».

### Подсказки (не проверены, проверить на этом модеме)

- У MediaTek есть AT-команда `AT+ECELL` (и URC `+ECELL`), которая отдаёт
  обслуживающую и соседние соты с уровнями; для LTE в ней бывает TA.
- Порт `wwan0mipc2` сейчас в игнорируемых. В протоколе MIPC есть запросы
  информации о базовых станциях — возможно, это более полный источник, чем AT.
- Инженерный режим `AT+EINFO` — запасной источник для TA и соседей.

### Заодно, если несложно

- Интерфейс `Modem.Signal` (`mmcli --signal-setup`): RSRP/RSRQ/SNR
  обслуживающей соты по подписке.
- Событие смены обслуживающей соты (сигнал `PropertiesChanged` на `Location`),
  чтобы не ловить хендовер опросом.

### Приёмка

1. `mmcli -m 0 --get-cell-info` и `mmcli -m 1 --get-cell-info` от пользователя
   `serlk` возвращают обслуживающую соту со всеми полями идентификации и
   уровнями.
2. В городе в выводе есть хотя бы несколько соседних сот с `physical-ci`,
   частотой и уровнем.
3. Во время активной передачи данных у обслуживающей LTE-соты есть
   `timing-advance`.
4. Вызов отрабатывает быстрее 1 секунды.
5. Опрос раз в 2 секунды в течение 10 минут: соединение не рвётся, входящий
   звонок проходит, значения меняются при движении.
6. В режиме полёта метод возвращает ошибку.

В ответ на задачу нужны: пример реального вывода для LTE (и NR, если
ловится), единицы Timing Advance, список полей, которые модем не отдаёт.

## 2. Bluetooth

Приложению нужны три сценария; все через стандартный D-Bus API BlueZ от
пользователя `serlk`.

1. **Пассивное BLE-сканирование для позиционирования.**
   - Адаптер виден как `org.bluez.Adapter1` и включается.
   - Работает `SetDiscoveryFilter` с `Transport=le` и `DuplicateData=true`:
     нужны повторные объявления с обновляющимся RSSI, а не одно на устройство.
   - Сканирование может идти непрерывно десятки минут.
2. **OBD-II адаптер ELM327 для скорости автомобиля.**
   - Большинство таких адаптеров — классический Bluetooth с профилем SPP,
     поэтому нужен BR/EDR и RFCOMM (сопряжение по PIN, `Profile1` или
     `/dev/rfcomm*`).
   - Часть адаптеров — BLE с GATT, нужен и он.
3. **Нода Meshtastic / MeshCore** (позже): BLE GATT с сопряжением по PIN,
   согласование MTU, уведомления.

Общие требования:

- Сканирование и одно-два активных соединения работают одновременно.
- Сканирование BLE не ломает Wi-Fi (чип, вероятно, общий) и звук по A2DP.
  Если есть ограничения по совместной работе, описать их.
- Доступ к BlueZ от `serlk` без root.

Приёмка: `bluetoothctl scan le` от `serlk` показывает устройства с
обновляющимся RSSI; ELM327 сопрягается и отвечает на `ATZ`; при этом Wi-Fi
остаётся подключённым.

## 3. Wi-Fi (небольшое дополнение)

Wi-Fi — основной источник точности, поэтому нужно то же самое для него:

- Пользователь `serlk` может запускать сканирование (`RequestScan` в
  NetworkManager или `Scan` в wpa_supplicant) без root и запроса прав.
- Сканирование можно запускать раз в 3–5 секунд, оставаясь подключённым к сети.
- В результатах есть BSSID, частота, уровень в dBm и возраст записи
  (`LastSeen`), чтобы отбрасывать устаревшие точки.
