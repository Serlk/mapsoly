# Offline routing

Routing engine: [Valhalla](https://github.com/valhalla/valhalla), always
reached through its HTTP JSON API. The Dart side (`lib/routing/`) is one
client; only the base URL differs between phone, PC and a remote server.

## Pinned versions

| What | Version | Where |
|---|---|---|
| Valhalla on the phone | **3.6.0** (`valhalla-3.6.0-r2`, Alpine v3.24 `community`) | `apk add valhalla` |
| Tile builder + PC backend | `ghcr.io/valhalla/valhalla:3.6.0` | `tool/build_routing.sh`, `lib/routing/native/valhalla_service_docker.sh` |
| Shim build sysroot | Alpine 3.24 aarch64 | `lib/routing/native/build_shim.sh` |
| Valhalla on Android | **3.6.0** built from source, static; Boost 1.83.0 (headers), protobuf 3.21.12 (lite), lz4 1.10.0 | `tool/build_valhalla_android.sh` |

Things that turned out different from the original plan:

* Alpine 3.24 has Valhalla 3.6.0 in its own `community` repo. 3.9.1 exists
  only in `edge/community` and cannot be installed on 3.24 without upgrading
  abseil (`so:libabsl_*.so.2608.0.0` missing), so it is not used.
* The Alpine package (3.6.0 and 3.9.1 alike) is built with
  `ENABLE_TOOLS=OFF ENABLE_SERVICES=OFF`: it ships `libvalhalla.so.3` and four
  Python scripts (`valhalla_build_config`, `valhalla_build_extract`,
  `valhalla_build_elevation`, `valhalla_build_timezones`) but **no
  `valhalla_service`** and no tile-building tools.
* So the phone runs `mapsoly_valhalla`
  (`lib/routing/native/valhalla_shim.cc`, 80 KB): a small HTTP server on top
  of `valhalla::tyr::actor_t` from the packaged library. Same command line
  (`<config.json> <threads>`) and same JSON in/out as `valhalla_service`.

Keep the builder image and the phone library on the same version. The config
is version-specific: a `valhalla.json` generated by 3.9.3 makes 3.6.0 refuse
to start (`Action not supported tile`, then
`No such node (service_limits.tile.max_locations)`). Tiles built by 3.9.3 did
load in 3.6.0 (121 tiles), but routing on them was not tested.

## Building tiles (PC)

    tool/build_routing.sh <pack-name>

Reads `data/packs/<name>/region.osm.pbf`, writes
`data/packs/<name>/valhalla/`:

* `tiles.tar` – the graph (indexed tar, mmapped by Valhalla);
* `valhalla.json` – config with paths relative to that directory
  (`tiles.tar`, `traffic.tar`), listen `tcp://127.0.0.1:8002`;
* `build.json` – Valhalla version, image, date, tile count.

Docker runs as the invoking user. `VALHALLA_IMAGE`, `CONCURRENCY` and
`KEEP_WORK=1` (keep loose tiles and `admin.sqlite` in `valhalla/work/`) can
be set in the environment.

Included: admin areas, built from the same PBF (`valhalla_build_admins`,
about 1 s for the test region). They are baked into the tiles and not needed
at run time.

Skipped:

* **Timezones** – `valhalla_build_timezones` downloads a world timezone
  shapefile; without it Valhalla cannot do time-dependent routing
  (`date_time` requests, predicted traffic). The client therefore does not
  send `date_time`.
* **Elevation** – no hill costing for bicycle/pedestrian, no `/height`.
* **Transit**.

## Running the backend

`RoutingBackend.forPack(packDir)` picks one of:

**Phone (Alpine)** – `LocalValhallaBackend` spawns `mapsoly_valhalla`:

1. needs `apk add valhalla` (pulls nothing else on the Titan 2 image);
2. build the binary on the PC: `lib/routing/native/build_shim.sh` →
   `data/routing-native/mapsoly_valhalla` (clang + lld against an Alpine
   aarch64 sysroot fetched via Docker; no qemu; the sysroot is ~730 MB and
   is reused);
3. ship it next to the app executable (`<bundle>/`, `<bundle>/lib/` or
   `<bundle>/data/`), or set `MAPSOLY_VALHALLA_BIN`, or put it in `$PATH`.
   `tool/deploy_titan2.sh` does not copy it yet.

The backend picks a free loopback port, writes a runtime config (absolute
paths, private IPC sockets) into a temp directory, waits for `/status`,
restarts the process after a crash (back-off 0.5 s, 1 s, 2 s…; gives up after
5 crashes in a row) and kills it on `dispose()`. The shim also exits by
itself when the app's end of its stdin closes, so it does not outlive a
killed app.

**PC** – either

* let the app spawn the real `valhalla_service` from Docker:
  `MAPSOLY_VALHALLA_BIN=$PWD/lib/routing/native/valhalla_service_docker.sh`, or
* run it yourself and point the app at it with `MAPSOLY_VALHALLA_URL`:

      cd data/packs/<name>/valhalla
      docker run --rm --network host -u $(id -u):$(id -g) -v $PWD:$PWD:ro -w $PWD \
        ghcr.io/valhalla/valhalla:3.6.0 valhalla_service valhalla.json 2
      MAPSOLY_VALHALLA_URL=http://127.0.0.1:8002 ...

**Remote server** – `RemoteValhallaBackend(uri)` / `MAPSOLY_VALHALLA_URL`.

**Android** – `LocalValhallaBackend` spawns the same shim, shipped inside the
APK; see [Android build](#android-build) below.

Manual end-to-end check (spawn, route, per-edge data, kill, restart, stop):

    dart run test/routing/manual_e2e.dart data/packs/<name>/valhalla [binary]

## Android build

Android has no libvalhalla to link against, so it is cross-compiled with the
NDK and linked statically into the shim:

    tool/build_valhalla_android.sh              # arm64-v8a and x86_64
    tool/build_valhalla_android.sh x86_64       # one ABI (x86_64 = emulator)

It needs the Android SDK with NDK 28.2.13676358 and the SDK's CMake (ninja
comes with it), plus git, curl, pkg-config, make and a host C++ compiler. No
root, no Docker. A first run downloads about 130 MB of sources and takes a few
minutes per ABI with 8 jobs; later runs only rebuild what is missing, and
relinking the shim after an edit takes seconds. Everything is kept in
`data/valhalla-android/` (`dl/`, `src/`, `host/`, `<abi>/build`,
`<abi>/prefix`, `logs/`).

Result: `android/app/src/main/jniLibs/<abi>/libmapsoly_valhalla.so`
(gitignored, so run the script before `flutter build apk`; without it the app
builds but has no routing). Stripped size: 8.2 MB (arm64-v8a), 8.5 MB (x86_64); about 2.5 MB each inside the APK.

How it fits together:

* The file is an **executable** with a library's name. An app may only exec
  files from its native library directory, and the installer only puts
  `lib*.so` there. `android/app/build.gradle.kts` sets
  `packaging.jniLibs.useLegacyPackaging = true` so that the libraries are
  extracted to disk at install time (the default is to map them from the APK,
  which cannot be exec'ed).
* `LocalValhallaBackend.findBinary` gets the native library directory from
  `/proc/self/maps` (the directory `libapp.so` / `libflutter.so` were loaded
  from), so no platform channel is involved.
* The runtime config goes to `Directory.systemTemp`, which the Flutter engine
  points at the app's cache directory. The `ipc://` entries in it are unused
  by the shim (they are for `valhalla_service`'s zeromq workers).
* The binary needs only `libc`, `libm`, `libdl`, `liblog` and `libz` from the
  system; libc++ is linked statically. API level 24, 16 KiB page alignment.
* Listening on 127.0.0.1 needs the `INTERNET` permission, which the app has.

Valhalla is configured with `ENABLE_DATA_TOOLS`, `ENABLE_SERVICES`,
`ENABLE_TOOLS`, `ENABLE_HTTP`, `ENABLE_GDAL`, `ENABLE_PYTHON_BINDINGS` and
`ENABLE_TESTS` all `OFF`. That removes mjolnir, prime_server/zeromq, curl,
gdal, sqlite/spatialite, luajit and geos; what remains is
baldr/loki/meili/midgard/odin/sif/skadi/thor/tyr and needs Boost headers,
protobuf-lite, lz4 and zlib (zlib comes from the NDK). The CMake options do
not go further than that: individual actions (isochrone, matrix, …) cannot be
left out, but `--gc-sections` drops part of the unused code at link time.
protobuf is pinned to 3.21.12 because later releases need abseil; the script
builds a host `protoc` of the same version for the code generator.

Known limits:

* 32-bit ABIs are not built. `armeabi-v7a` is accepted by the script but was
  never tried.
* Verified on the x86_64 emulator only (Android 14, API 34), by running the
  binary from `adb shell` on a pack's routing data: `/status`, `/route`
  (auto, 80 km: 0.59 s for the first request; pedestrian), `/locate` and
  `/trace_attributes` answered, 115 MB resident afterwards. The arm64 binary
  is built the same way but has not been run on a device, and the path
  through the installed app (exec from the native library directory) has not
  been exercised yet.

## Measured numbers

Test region: Geofabrik `russia/kaliningrad`, 2026-11-26.

| | |
|---|---|
| `region.osm.pbf` | 29.3 MB |
| `tiles.tar` | 26.1 MB, 121 tiles |
| `tool/build_routing.sh` on the PC | 11 s in total |

Unihertz Titan 2, `mapsoly_valhalla` with 2 threads, tiles built on the PC,
requests from the phone itself over 127.0.0.1:

| Request | Time |
|---|---|
| spawn until `/status` answers | 240–270 ms |
| auto, 42 km, 2 alternates (3 routes returned) | 48–65 ms warm, 280 ms first request |
| auto, 122 km, 2 alternates | 61–66 ms |
| pedestrian 33 km, 2 alternates / bicycle 35 km (2 routes) | 215 ms / 157 ms |
| pedestrian / bicycle 4.7 km | 23 ms / 25 ms |
| `/trace_attributes` for one 42 km route (235 edges) | 13–14 ms with curl, 15–40 ms from Dart |
| resident memory after those requests | 88 MB (includes mmapped tile pages) |

The central-federal-district pack was not built or measured (its PBF was
still downloading). Expect tile size of the same order as the PBF.

## Traffic

### v1: re-estimate alternates from traffic tile colours

1. `client.route(locations: …, alternates: 2)` → up to 3 `Route`s with full
   `shape`.
2. For each, `client.edges(route)` → `List<RouteEdge>`: per directed edge
   `id`, `wayId`, `lengthMeters`, `speedKmh` (the speed Valhalla assumed),
   `freeFlowSeconds` (edge traversal plus the turn onto it),
   `beginShapeIndex`/`endShapeIndex` into `route.shape`, `roadClass`.
3. The sampler reads colours along `shape[begin..end]` of every edge and
   computes e.g. `Σ max(freeFlowSeconds, lengthMeters / trafficSpeed)`.

`edges()` calls `/trace_attributes` with the leg's own encoded shape and
`shape_match: edge_walk`, which only re-walks the known path: one extra
request of 13–40 ms per route on the phone. In the test the edge times add up
to the route time within 0.1 min. `/route` itself has no per-edge output in
3.6.0, so this is the recommended source. Without the extra request the
coarser fallback is per maneuver: `Maneuver.beginShapeIndex/endShapeIndex`,
`lengthMeters`, `timeSeconds`.

`edge_walk` can fail on odd geometry; `edges()` then retries with
`map_snap` (slower, may differ slightly). Not seen in testing.

### v2: Valhalla live traffic (not implemented)

Valhalla reads live speeds from `mjolnir.traffic_extract` (`traffic.tar`): one
fixed-size record per directed edge, mmapped, so it can be rewritten while
the service runs. The pack config already points at `traffic.tar` next to
`tiles.tar`.

What is there on the phone (Alpine `valhalla-3.6.0-r2`):

* `valhalla_build_extract` **is** included (Python) and has
  `-t/--with-traffic` "add a traffic.tar skeleton". It works from loose tiles
  in `mjolnir.tile_dir`, which the pack does not ship; simpler to add
  `--with-traffic` to `tool/build_routing.sh` and ship the skeleton.
* libvalhalla tries to load the traffic extract at start-up (log line
  `Traffic tile extract could not be loaded` when the file is missing).
  Routing with a filled `traffic.tar` was **not** tested.
* No tool that writes speeds exists, neither on Alpine nor upstream.

What v2 needs:

1. **Skeleton** `traffic.tar` built together with `tiles.tar` (same build:
   edge ids change on every tile build, see `RouteEdge.id`).
2. **A writer**: C++ against `valhalla/baldr/traffictile.h` (`valhalla-dev`),
   filling `TrafficSpeed` records (overall speed, up to three sub-segments,
   congestion) and the tile's `last_update`. It fits into the shim as an
   extra endpoint, since the shim already links libvalhalla.
3. **Edge mapping**: traffic sources give geometry, Valhalla wants edge ids.
   Either enumerate all edges with shapes once per build
   (`valhalla_export_edges`, `valhalla_ways_to_edges` – both in the Docker
   image, not on Alpine) and sample colours per edge, or only update the
   edges near candidate routes using `RouteEdge.id` from `/trace_attributes`
   (cheap, but the search cannot avoid jams it has not been told about).
4. **Request side**: live speeds are used for time-aware requests
   (`date_time` type 0 = "now"); that most likely requires the timezone DB
   skipped above. To be verified first.
